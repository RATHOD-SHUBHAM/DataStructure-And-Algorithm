What does “square root rounded down” means.

Step 1: What is the square root?

The square root of x is the number that, multiplied by itself, gives x.

  • √4 = 2, because 2 × 2 = 4
  • √9 = 3, because 3 × 3 = 9

Step 2: What does “rounded down” mean?

For x = 8, the real square root is 2.828..., and we need the whole number just below it, which is 2.

Ask what that “whole number just below” means in terms of multiplication:

  • 2 × 2 = 4, which is at most 8, so 2 is okay.
  • 3 × 3 = 9, which is more than 8, so 3 is too big.

So the answer is the biggest whole number whose square doesn’t go over x.

Step 3: Write that as math

“Whose square doesn’t go over x” means k * k <= x.

So k*k <= x isn’t a trick, it’s just the definition said with symbols: “the biggest k where k times k is still not more than x.”

Step 4: Why is this useful?

It lets us test any guess without computing a square root. Try guesses for x = 8:

kk*kk*k <= 8 ?
11yes
24yes
39no
416no

The yes answers come first, then the no answers, and they never switch back. Because the pattern is yes, yes, no, no, we can binary search it, and the answer is the last “yes”.

Sqrt(x): how to approach it in an interview

1. Clarify first (30 seconds)

  • Is x always non-negative? Yes: 0 <= x <= 2^31 - 1.
  • Do we round down (floor)? Yes.
  • Can I use * or math.sqrt? No.

Asking these shows you read the constraints, and the answer to the second one tells you the problem is really “find the largest integer k with k*k <= x”.

2. Brute force (say it out loud, then move on)

k = 0
while (k + 1) * (k + 1) <= x:    
	k += 1
return k

This is O(√x) time. For x near 2³¹ that’s about 46,000 steps, which is fine, but the interviewer will want better.

Why (k + 1)

In that loop, k always holds a number that is already known to work (k*k <= x). Before moving up, we ask: “would the next number, k + 1, also work?”

  • If yes, move to it (k += 1).
  • If no, stop. k is the biggest one that works.

So the loop peeks one step ahead, and when it ends, k is the answer with nothing to adjust.

Trace for x = 8:

k(k+1)²(k+1)² <= 8 ?action
01yesk = 1
14yesk = 2
29nostop, return 2

3. The key observation

Look at k*k <= x for k = 0, 1, 2, 3, ... with x = 8:

k:        0     1     2     3     4     5 ...
k*k<=8:  True  True  True  False False False

The answer is the last True. The results go True...True False...False, so the sequence is monotonic, and monotonic means binary search. This is the same two-zone idea from Search Insert Position, just flipped:

  • Search space: k from 0 to x. You’re searching over candidate answers, not over an array.
  • Predicate: k*k <= x.
Saying “the predicate is monotonic, so I can binary search on the answer” is the line interviewers listen for.

4. Solution A: bisect style (the template you already know)

Find the first k where k*k > x. The answer is one less than that.

The values k*k <= x form a block of “good” numbers, followed by a block of “bad” numbers (k*k > x). The first bad k sits right at the border, so the last good one is the element immediately to its left, which is k - 1.

This is also why bisect_right fits. It returns the first index where the value is strictly greater than the target, and the last valid element is one position before that

def mySqrt(x):
    left, right = 0, x + 1        # right = x+1 so "none found" is representable, eg ip: x = 1
    while left < right:
        mid = (left + right) // 2
        if mid * mid <= x:
            left = mid + 1        # mid still works, look right
        else:
            right = mid           # mid too big, keep as candidate for "first too big"
    return left - 1

This is the bisect_right shape (<= goes right) applied to the squares.

5. Solution B: track the answer (often easier to explain)

Find the last good k, where k * k <= x

def mySqrt(x):
    left, right = 0, x
    ans = 0
    while left <= right:
        mid = (left + right) // 2
        if mid * mid <= x:
            ans = mid             # valid, save it and try bigger
            left = mid + 1
        else:
            right = mid - 1
    return ans

Same logic, but the “keep mid as a candidate” step is an explicit ans = mid. Pick whichever you can explain without hesitating. Many people find B more intuitive under pressure.

6. Edge cases to mention

  • x = 0: returns 0. x = 1: returns 1. Both work with the code above, but say that you checked them.
  • Perfect squares (x = 4): mid*mid == x falls into the <= branch, and the search continues right and settles on 2.
  • Large x (2³¹ - 1): Python integers don’t overflow. In Java or C++, mid * mid can overflow int, so use long or compare mid <= x / mid. Mentioning this is a strong signal even if you’re coding in Python.
  • Optional speedup: for x >= 2, the root is at most x // 2, so you can start with right = x // 2. It’s a constant-factor gain and not required.

7. Complexity

  • Time: O(log x), about 31 iterations at most.
  • Space: O(1).

8. Likely follow-up: Newton’s method

If asked “can you do it faster or without binary search?”:

def mySqrt(x):
    r = x
    while r * r > x:
        r = (r + x // r) // 2
    return r

It converges quadratically (the number of correct digits roughly doubles each step), so it takes very few iterations. Trace for x = 8: r goes 8, 4, 3, 2, then stops. When x = 0, the loop never runs, so there’s no division by zero. You don’t need to derive it, but being able to name it as “Newton-Raphson on f(r) = r² - x” is a plus.

The idea

Say you have a guess r that is too big (r * r > x). Then x // r is too small.

Why: r * (x / r) = x. If r is bigger than the true root, the other factor x / r has to be smaller than the true root. The two factors multiply to x, so one sits above the root and one sits below.

So the real root is trapped between x // r and r. Averaging them gives a better guess:

new r = (r + x // r) // 2

Repeat until the guess is no longer too big (r * r <= x).

Questions you might have

Why start with r = x?

  • Any starting guess that is at least the true root works, and x always is (for x >= 1). It’s the simplest choice.

Why does it stop at exactly the floor?

  • Starting from above, each new guess is never smaller than the true floor root, and the guesses keep going down. So the first time r * r <= x becomes true, r is the largest whole number that fits, which is the floor.

What about x = 0?

  • r = 0, and 0 * 0 > 0 is false, so the loop never runs and we return 0. This also means x // r is never evaluated with r = 0, so there’s no division by zero. For x = 1, the same thing happens and it returns 1.

In an interview

Binary search is the expected main answer. Mention Newton’s method only as a follow-up when asked for something faster. Binary search takes about 31 steps at most, while Newton’s method takes roughly 6 to 8 for the largest inputs. You don’t need to prove convergence, but you should be able to say “if r is too big, x // r is too small, so I average them.”

The core idea

Newton’s method finds where a function equals zero. To get a square root, we turn the problem into a zero-finding problem:

sqrt(x) is the r where r² - x = 0

So define f(r) = r² - x. The root of f is sqrt(x), which is the green dot in the drawing.

The trick: you can’t solve a curve directly, but you can solve a straight line. So at your current guess, draw the tangent line (a straight line that matches the curve’s slope there), and see where that line hits zero. Use that point as your next guess. A tangent is a good stand-in for the curve nearby, so the next guess is much closer.

Where the formula comes from

The slope of f(r) = r² - x at r is 2r. The tangent line at the current guess r goes down by f(r) over a horizontal distance of f(r) / slope, so:

new r = r - f(r) / slope
      = r - (r² - x) / (2r)
      = (2r² - r² + x) / (2r)
      = (r² + x) / (2r)
      = (r + x/r) / 2

That is exactly the averaging formula from the code. The average of r and x/r isn’t a coincidence: it is the tangent line’s landing spot.

Why it never overshoots below the root

For any positive r, the average of two numbers is at least as large as their geometric mean:

(r + x/r) / 2  >=  sqrt(r * x/r)  =  sqrt(x)

So after the very first step, every guess is at or above the true root. The guesses only come down from above, which is why the integer version can stop at the first r * r <= x.

The integer version

Real-number Newton on x = 8 gives 8, 4.5, 3.14, 2.84, 2.83, and so on. In the code we use //, which floors each step, so the guesses become whole numbers: 8, 4, 3, 2. The loop stops the first time r * r <= x. Since the guesses decrease from above, that first r is the largest whole number whose square fits, which is the floor of the root.

def mySqrt(x):
    r = x
    while r * r > x:
        r = (r + x // r) // 2
    return r

Speed

Near the root, the number of correct digits roughly doubles each step (quadratic convergence). I need to correct something I said earlier, though. Starting from r = x is a poor guess for big inputs, because while the guess is far above the root it only about halves each step. For x = 2³¹ - 1, that takes around 20 steps in total, and that’s still fewer than the ~31 for binary search, but not dramatically so. A good starting guess, such as a power of two near sqrt(x), brings it down to about 5 steps.

Interview framing

  • Binary search on the answer is your main solution. It’s easy to get right and easy to explain.
  • Mention Newton’s method as a follow-up, in one sentence: “If r is too big, x // r is too small, so I average them, and that’s Newton-Raphson on r² - x.”
  • Don’t lead with it unless asked. A small off-by-one in the loop condition or the starting value is much easier to make here than in binary search.
